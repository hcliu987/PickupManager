# R2 — 解析器正确性（H-01 及其同源缺陷）

**本轮目标**：把"解析出来的东西是不是真的取件码"这件事钉死。
**结论**：不是。驿站短信几乎必带一个联系电话，而通用码形是**全文无约束**匹配 ——
用户拿到的是别人手机号的片段，而且它会一路走到一键复制和一键分享。

| 条目 | 内容 | 状态 |
|---|---|---|
| H-01 | 手机号 / 服务号 / 日期 / 时刻 / 金额被切成取件码 | **已修** |
| L-（本轮回填） | `matcher.group(1)` 平台类型直接 `add()`，改动正则会静默变 NPE | **已修** |
| — | 正则灾难性回溯（ANR 风险） | **已验证无问题**（加了回归用例守住） |

## 1. 先说证据，再说修法

修之前先写了 6 个用例把缺陷钉成**红的**（`ParserPhoneNumberRegressionTest.kt`）：

```
ParserPhoneNumberRegressionTest > 日期时间与金额不得被当成取件码 FAILED
ParserPhoneNumberRegressionTest > 凭手机号取件的短信不应产出任何取件码 FAILED
```

这一条很重要：如果只报"已修复"而拿不出"修复前是坏的"，那这句话没有信息量。
四个红灯分布在四条不同的输入上，不是同一个 bug 换四种说法。

## 2. 缺陷机理

`GENERIC_CODE_PATTERNS` 的最后两条是：

```kotlin
Pattern.compile("\\d{2,4}-\\d{3,4}")   // 数字-数字
Pattern.compile("\\d{4,8}")            // 纯数字
```

`Matcher.find()` 的行为是"在任意位置找最长可行匹配"，于是对

```
【驿收发】您的包裹已到示例小区快递柜，编号8823，咨询18712345678
```

`\d{4,8}` 在 `18712345678` 上先吃掉 `18712345`，下一轮再吃掉 `45678`。
两个都不是取件码，但都满足"4~8 位数字"，于是入库、上屏、`ShareUtils`
一键分享出去。**用户点"复制取件码"，粘出来的是号码片段。**

已有的那道防线为什么没拦住：

- `PickupCodeExtractorV3.isValidCode()` 里确实有手机号排除，但（a）它**不在主路径上**
  （主路径是 `RuleBasedPickupParser`），（b）它要求 `code` 与手机号**整串相等**，
  而这里被切成的是**片段**，相等判定天然失效。
- 引导词优先（策略 0）能盖住大部分短信，但盖不住"没有引导词的新快递模板"——
  而这恰好是新快递公司上线时的常态。

## 3. 修法：先脱掉"不可能是码的东西"，再谈码形

**为什么不给每条正则加邻近约束**：`GENERIC_CODE_PATTERNS` 有 7 条，
`SIGNATURE_FORMATS` 里还有几十条按快递公司写死的码形。给它们逐条加
"必须距离取件码/凭/输入 若干字符以内"的约束，等于把一处缺陷变成四十处，
而且每加一条都可能误杀某个真实快递的合法码（比如丰巢的 4 位码可能离引导词很远）。
上一轮作者已经因为"给正则打补丁"吃到过苦头（`CODE_PREFIX_PATTERNS` 上方那段注释就是）。

**采用的修法**：抽取前复制一份短信，把**已知不可能是取件码的数字段落**
用**等长**的 `U+FFFD` 顶掉，只在副本上跑码形匹配。

```kotlin
private val NON_CODE_NUMERIC_PATTERNS = listOf(
    Pattern.compile("(?<!\\d)(?:\\+?86[- ]?)?1[3-9]\\d([- ]?)\\d{4}\\1\\d{4}(?!\\d)"), // 手机号
    Pattern.compile("(?<!\\d)[48]00[- ]?\\d{3}[- ]?\\d{4}(?!\\d)"),                     // 400/800
    Pattern.compile("(?<!\\d)0\\d{2,3}[- ]?\\d{7,8}(?!\\d)"),                          // 座机
    Pattern.compile("(?<!\\d)(?:19|20)\\d{2}[-/.年]\\d{1,2}[-/.月]\\d{1,2}日?(?!\\d)"), // 日期
    Pattern.compile("(?<!\\d)\\d{1,2}:\\d{2}(?::\\d{2})?(?!\\d)"),                      // 时刻
    Pattern.compile("[¥￥$]\\s?\\d+(?:\\.\\d{1,2})?|\\d+(?:\\.\\d{1,2})?\\s?(?:元|块钱|块|分钟|小时|天|个月|年|%|折)"),
    Pattern.compile("(?<!\\d)\\d{11,}(?!\\d)")                                          // 长数字串
)
```

**四个设计点，每个都有理由**：

1. **等长替换**（不是删除、不是 `replace` 成短占位符）。
   长度不变意味着所有位置约束、以及后续任何 `substring` 类操作不会整体错位 ——
   上一轮就是被"长度变了但没人发现"坑过一次（见 `01-desensitization.md` §4 的行号问题）。
2. **用 `U+FFFD` 做填充**。它不可能出现在任何码形里，所以"结果里含占位符"
   等价于"这个候选来自被顶掉的段落"，一条 `filterNot { it.contains(REDACTED) }`
   就把引导词路径、签名路径、通用路径三条出口一起兜住了。
3. **日期只认 `19xx` / `20xx` 开头**。写成裸 `\d{4}[-/]\d{1,2}[-/]\d{1,2}`
   会把 `1234-5-6789` 这种真实四段取件码整段吞掉 —— 这个取舍写在代码注释里，
   不是随手写的正则。
4. **只在取件码抽取里用副本**。`AddressMatcher`、`extractTracking`、`cleanAddress`
   继续吃原始短信，因为它们本来就需要真实数字（`1号楼`、`运单尾号3321`）。

### 3.1 为什么不用 `android.util.Patterns.PHONE`

这是能查到的最权威的手机号正则，但它是 **Android 平台的类**，
在本项目的单元测试（纯 JVM，无 Robolectric）里**取不到**。
用它就意味着要么放弃这条回归用例、要么引入 Robolectric 这一整套依赖。
两者都比"手写一条带 `(?!\d)` 边界的正则"代价大，所以选择手写，并把边界写清楚：

- 前面 `(?<!\d)`、后面 `(?!\d)` —— 防止从更长的数字串中间切一段出来，
  这正是本缺陷的病灶；
- `([- ]?)\1` 反向引用 —— 允许 `187-1234-5678` 这类带分隔的写法，
  但**要求两端分隔符一致**，避免把 `1234-5678`（真实取件码）误当手机号。

参考资料：短信验证码/取件码抽取的通行做法是"发送方 + 关键词锚定 + 业务字段
白/黑名单"，而不是一条万能正则；本次检索确认了这一点，并确认
`Patterns.PHONE` 的实现依赖 `libcore`，不能在 JVM 单测里直接调用。

## 4. 顺带修掉的静默 NPE（同源）

编译器对 `RuleBasedPickupParser.kt` 有两处告警：

```
w: ...RuleBasedPickupParser.kt:686:37 Java type mismatch: inferred type is 'kotlin.String?', but 'kotlin.String' was expected.
w: ...RuleBasedPickupParser.kt:831:31 Java type mismatch: inferred type is 'kotlin.String?', but 'kotlin.String' was expected.
```

两处都是 `trackingNumbers.add(matcher.group(1))` / `addresses.add(matcher.group(1))`。
`Matcher.group()` 是 Java 平台类型，Kotlin 不做空检查就交给 `add()`。
今天正则里第 1 组必然存在，所以不会炸；**但只要有人把该组改成可选
（`(...)?`）或加一层不影响语义的分组，这里立刻变成一条没有任何提示的 NPE，
而且是运行到那条短信才炸。** 这不是洁癖问题，是一颗定时炸弹，
改动 2 行就能拆掉，所以在本轮一并处理。

## 5. 灾难性回溯：验证结论是"没有"

`ADDRESS_PATTERNS` 里有 `[..][..]{1,18}(?:40 个后缀之一)\d{0,4}(?=...)` 这种形状，
天然的嵌套量词风险。解析跑在 `SmsReceiver.onReceive` 的同步段里，
一旦回溯爆炸，后果不是"慢"而是 **ANR**。所以本轮**实测**而不是目测：

- 构造 400 段最恶劣输入（反复出现 `到达/已到/抵达/在` + 全套地址后缀字），
  断言单条 < 3000ms（实测远低于此）。
- 正常短信重复解析 1000 条，断言总耗时 < 3000ms。
- 两条都进了 `ParserRobustnessTest.kt`，以后谁改动地址正则、把复杂度提上去，
  CI 会直接红。

## 6. 本轮新增的三个测试文件

| 文件 | 作用 |
|---|---|
| `ParserPhoneNumberRegressionTest.kt` | 6 条：修复前 4 红。号码/服务号/日期/时刻/金额不得成为码 |
| `ParserRobustnessTest.kt` | 8 条：回溯耗时、空输入、截断短信、引号、占位符不外泄、地址不带引导词 |
| `RuleBasedPickupParserTest.kt`（既有） | 14 条：行为基线，本轮**未改任何断言**，全绿 |

### 关于"未改任何断言"

R1 因为统一示例地名动过既有测试的**字符串字面量**（`幸福小区`→`示例小区`）。
R2 不同：既有 14 条基线断言**一个字都没动**，新增行为全部由新文件承载。
区分这两者是必要的 —— 改被测对象的字符串是脱敏，改断言是改语义，
后者需要单独的、更强的理由。

## 6. 地址里的动作引导词：一个"尸体常量"引出的缺陷（H-15，R2 新发现）

写 `ParserRobustnessTest` 时顺手加了一条"地址不该带着动作引导词入库"的断言，
它**红了**。查下去发现不是新问题，是一直在那里、只是没人断言过：

```kotlin
// 地址前缀词表（用于清洗地址开头的多余字符）        ← 注释是这么写的
private val ADDRESS_PREFIX_WORDS = listOf("到达", "已到", "抵达", "到", "在", "位于")
```

`grep -n ADDRESS_PREFIX_WORDS` 的结果只有两行：**声明那一行，和注释那一行**。
没有任何代码读它。于是 `ADDRESS_PATTERNS` 的模式 3
（`([\u4e00-\u9fa5][...]{1,19}(?:小区|花园|...))` —— 没有引导词锚点，
可以从任意汉字起匹配）把动作词一起吃进地址：

```
输入：取件码 6-2-1188，已到示例小区3号楼驿站
地址：已到示例小区3号楼        ← 修之前
地址：示例小区3号楼            ← 修之后
```

修法是**让那个常量真的被用上**，并把它改名为 `ADDRESS_LEADING_ACTION_WORDS`，
同时收窄内容：只留两字及以上的词。原因写进了代码注释 ——
单字 `在` / `到` 会截断「在水一方小区 15 号楼」这类真实小区名。

这一条值得单独成节，因为它和 H-13（同一个地址标签有三套生成规则）加起来说明
一个模式：**这个项目的地址处理层是靠注释在描述意图的，代码并不执行那个意图。**
"注释与实现不符"在这里不是洁癖问题，是缺陷成因。

**读得再细也会漏，只有断言会一直盯着。**
