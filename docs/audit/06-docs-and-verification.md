> **本轮主题**：R1–R5 一直在产出"可核对的数字"，而**核对这些数字的机制本身**是最后一块没被验的东西。
> 本轮只做三件事：把错掉的数字改对、**并交给脚本复算**；把两个过弱的校验器补到
> "能抓住已经发生过的漏报"；把仓库自带的检查挂进 CI。

> **本轮只改一处 Kotlin 与一处 XML**（`widget/PickupWidgetService.kt`、
> `res/layout/widget_pickup_item.xml`，兑现 R4 移交的 L-07，见 §5.4），
> 其余改动全在文档与工具里。因此 Android 单测的结论**应当且只能**与 R5 一致，见 §7.1。

## 1. H-14：README 里那批数字，逐条改对并写明口径

### 1.1 错在哪

H-14 的原话已经说准了：README 用"逐条可核对""机械校验"支撑读者对它**全部**数字的信任，
而**这个强度超出了工具的能力**。上一版 `check_doc_refs.py` 只查两类东西：
`文件:行号` 是否越界、「包职责」表里每个包的文件数。其余数字（中文串数、测试用例数、
XML 硬编码中文数）**没有任何代码复算过** —— 写错了也没人会发现。

当场复算的结果：

| README 原话 | 实际 | 性质 |
|---|---|---|
| Kotlin 含中文串字面量 **819 处** | **1376** | 口径没写下来：同一仓库、同一问题能数出 819 / 1375 / 1376 三个值 |
| 布局与资源 XML 里的中文 **为 0** | **29 处** | 纯粹的错（8 个小部件布局的 `android:text` 与提示文案）。R6 末因 §5.4 删掉两条示例文案，现为 **28** |
| `res/values/strings.xml` 剩 **24 条** | **25** | 差 1 |
| 单元测试 **34 个用例** | **83**（其中 2 个门控） | R2–R5 一路在加，README 没跟 |
| `util/` 包 **21** 个文件 | **23** | 同上 |
| 「合计 **75** 个主源文件」 | **77 个文件 / 21527 行** | 同上。R6 末因 §5.4 那 6 行注释，行数再变成 **21533**（见 §7.2） |
| 13 处 `文件:行号` | 全部整体漂移 | 工具不校验锚点（见 §2） |

### 1.2 修法：口径与复算必须一起做

只改数字不够 —— 819 这个数字之所以能存在，是因为**"含中文的字符串字面量"从来没有定义**。
所以本轮做三件事：

1. **把口径写进 README 正文**："先剔除注释，再统计双引号字面量里含中日韩汉字的个数"。
   （口径写在数字旁边，读者才能判断它是不是自己要的那个数。）
2. **让 `check_doc_refs.py` 自己算**：新增 `gather_numbers()`，把能机械复算的 8 项
   （主源文件数 / 行数、中文串数、XML 硬编码中文数、`strings.xml` 条目数、单测数、门控数）
   全部重算，再拿 README 里的声明去比。**删掉那句声明也算失败** ——
   不许靠"把数字删了"过关（否则下次改动的动机就变成删数字而不是改对）。
3. **抽出 `tools/audit/kotlin_lexer.py`**：中文串统计与图标检查都需要"先剥掉注释与字符串"，
   两边各写一份就是 R5 踩过的那个坑（测试在复制品上通过、真工具反而没被覆盖）。

> 数字为什么会有三个值：`//` 出现在字符串里会把"按行剥注释"的朴素实现截断；
> `/* */` 嵌套、`"""` 原始串、`\` 转义各要处理。实现与用例见
> `tools/audit/kotlin_lexer.py` 与 `tools/audit/test_kotlin_lexer.py`（17 个用例）。

## 2. M-05：`check_doc_refs.py` 的六个缺口

M-05 报的是"锚点校验过弱"。把工具打开逐条看，实际是**六个**独立缺口，
而且它们互相掩护：只要有一个没修，已知的两处 `+7` 行漂移就照样漏网。

| # | 缺口 | 后果 | 修法 |
|---|---|---|---|
| 1 | `FILE_REF` 只认单个行号 | ``Foo.kt:12-34`` / ``Foo:594, 1137`` / ``Foo:1000/1019`` 三种写法整批不被校验 | 新增 `expand_numspec()`，把行号规格拆成 `[(lo, hi)]` 列表逐个查 |
| 2 | **逗号列表里的第二个数从来没被查过** | ``Foo:594, 1137`` 里的 `1137` 是装饰品 | 同上（这是最容易漏的一个：第一个数通过就整行通过了） |
| 3 | 锚点窗口 ±4/5 行，且"句中任一标识符命中即通过" | ±3 以上的漂移**必然**漏报 | 窗口收紧到 **±2**；先做行数越界与锚点两道判断，各自独立报错 |
| 4 | 反引号里的**裸类名**引用只判越界、从不校验锚点 | ``PickupSmsParserV2:1000/1019`` 漂到哪都不会被发现 | 裸类名也走 `anchor_err()`，并按 `lo..hi` 展开成区间 |
| 5 | 数字不复算（H-14） | 见 §1 | 新增 `gather_numbers()` + `check_doc_numbers()` |
| 6 | 符号池只装 Kotlin | 文档一旦引用仓库自己的 Python 工具函数就被误报"符号已不存在" | `load_sources()` 把 `tools/**/*.py` 一并加入符号池（不影响按目录数 `.kt` 的那条规则） |

### 2.1 怎么证明修好了 —— 用一个"负向测试"，而不是再读一遍代码

R6 新增 `tools/audit/test_check_doc_refs.py`：把**真实的 README** 复制到临时目录，
只改副本，喂给检查器，断言它抓得到、并且原 README 一个字节都没被碰。4 个用例、11 个突变（R7 加了「审计工具自测用例数」这一项）：

| 突变 | 期望 |
|---|---|
| 把某个行号改成不存在的位置 | 报"行号越界" |
| 把行号挪到 `±3` 以外（但仍在文件范围内） | 报"锚点对不上"——**这是旧工具必然漏报的那一种** |
| 改逗号列表里的**第二个**数 | 报错（缺口 2 的回归） |
| 把计数类数字改错 | 报"数字不符" |
| **删掉**那句数字声明 | 报"找不到这项声明" |
| 引用一个被删掉的裸类名 | 报错（缺口 4 的回归） |

在这套测试之前，R6 对增强版工具做过一次实际检验：把它指向未修的 README，它一次报出
11 处失效；改完之后又多抓出 3 处此前从未被发现的漂移
（`MainScreen:240`、`ComposeMainActivity` 的裸类名、`AndroidManifest.xml:95-99`）。
**工具变强这件事本身需要有证据，否则只是"我觉得更严了"。**

## 4. 本轮的两次自纠，和它们共有的那个模式

这两次都不是"发现新缺陷"，而是**发现已经写进报告的东西是错的**。放在一起看，它们形状一样：

| | 第一次（R5 §10.1） | 第二次（R5 §11） |
|---|---|---|
| 写了什么 | "全仓剩余编译警告 2 条" | "同一字符串 16 次只标 3 处，判定自相矛盾" |
| 错在 | 用的是**增量构建日志**，未重编译的文件不产生警告 | 把工具输出的**聚合计数**当成了单值计数 |
| 共同点 | **两者都是"取了一个不能代表全体的量"**：一个是"增量日志代表全仓"，一个是"两个值的合计代表其中一个值" |  |

所以 R6 的结论不是"下次小心点"，而是一条可执行的规则：

> **凡是写进报告的数字，要么当场用一条命令复算出来，要么标注它是哪一刻、哪个子集的观测值。**
> 两者都不行的，就不写。

这条规则现在已经部分机械化了 —— 8 项计数声明由 `check_doc_refs.py` 复算。
剩下那些"必须标注时点"的数字（比如扫描器的命中数会随仓库内容移动）在 §5.6 里标了时点。

## 5. CI 收口：本轮新接入的 7 步门禁，和一个必须项

### 5.1 接线

`.github/workflows/android.yml` 现在在**构建之前**新增 7 步、共 10 条命令
（CI 的构建前门禁合计为 **9 步 / 12 条**）：

```
审计工具的自我测试（4 个测试文件，50 个用例）
工作树里没有敏感数据      scan_sensitive.py .
git 历史里没有敏感数据     scan_history.py .
提交元数据已脱敏          scan_commit_identity.py .
没有死掉的图标 import      check_icon_imports.py .
.gitignore 能挡住嵌套路径   check_gitignore_depth.py .
缺陷总表结构自检          check_ledger.py .
```

原本已在 CI 里的两条（`check_doc_refs.py`、`check_log_privacy.py`）继续保留。

### 5.2 必须项：`fetch-depth: 0`

`actions/checkout` 的默认值是 `fetch-depth: 1`。在浅克隆上，`scan_history.py`
会"扫完"并打印 `✓ 历史对象里没有 BLOCK 级命中` —— **而它其实只看见一个提交**。
一个看起来通过的门禁比没有门禁更危险，这条与 §4 是同一个模式的第三次出现，
所以写进 workflow 的注释里，也写进 README。

### 5.3 本轮把 `tools/audit/*` 接进 CI 时发现的两件事

- `scan_sensitive.py` 在接入**之前**是失败的（退出码 1）。原因见
  `05-security-and-license.md` §15.6 的对比表：旧版的豁免判定既漏（真实域名邮箱被放过）
  又错（把 19 位银行卡号因含子串 `12345678901` 而判为示例）。**先修判定，再接门禁** ——
  否则唯一的后果是把 CI 改成红的，然后有人会去关掉它。
- `scan_sensitive.py` 的自我测试文件**自己**会撞上这个门禁：它需要"看起来真实"的号码
  才能证明豁免表不过宽。修法与由此暴露的能力边界，见 `05-security-and-license.md` §15.7
  （**正则扫描是可绕过的，它提高成本，不做证明**）。

### 5.4 L-07（R4 移交本轮）：越界请求会把示例文案渲染成"一条包裹"

R4 的总表把它标成"移交 R6"，本轮兑现。缺陷是两半：

1. `res/layout/widget_pickup_item.xml` 里 `item_pickup_code` 与 `item_address` 两个
   TextView 的默认文案被写成了示例数据：`android:text="ABCD1234"` 与 `"菜鸟驿站"`。
2. `PickupWidgetService.getViewAt()` 的越界分支**直接 `return views`**，一条文本都不设。

于是"数据在刷新瞬间变化、ListView 仍请求越界位置"时，渲染出来的是布局里那两条写死的
示例文案 —— 用户看到一条不存在的包裹，而 `ABCD1234` 长得就像一个真取件码。

修法（两半都修，只修一半都还会复现）：

```kotlin
if (position >= pickupItems.size) {
    views.setTextViewText(R.id.item_pickup_code, "")
    views.setTextViewText(R.id.item_address, "")
    return views
}
```

并把布局里那两条示例文案改成空串（它们的值本来就永远由代码写入，留着默认值是纯陷阱）。

> **这一改立刻被 §5 的门禁抓住了一次 —— 值得记下来，因为它说明门禁真的在工作。**
> 改完之后 `check_doc_refs.py` 报出 **3 处失效**，其中两处跟我改的布局无关：
>
> ```
> !! 3 处失效：
>    README  包职责节的「主源文件数与行数」: 文档写 (77, 21527)，实测 (77, 21533)
>    README  构建注意事项里的「106→N 个 / 28877→M 行」: 文档写 (77, 21527)，实测 (77, 21533)
>    README  问题 8 的「XML 硬编码中文文案数」: 文档写 (29,)，实测 (28,)
> ```
>
> - `29 → 28`：因为删掉了 `菜鸟驿站` 这条硬编码中文（预期之中）。
> - `21527 → 21533`：因为**我在 `PickupWidgetService.kt` 里加了 6 行注释**。
>   这一条没人会想到要去改 README —— **是脚本自己算出来的**。
>   这就是 §1 那条改动的全部意义：文档里的数字不再依赖"记得去改"。

### 5.5 为了写 §8 的统计，顺手抓到：总表自己不能被机械读出

`99-final-report.md` 的缺陷统计必须来自 `00-defect-ledger.md`。于是 R6 写了一个
30 行的解析器去数它 —— **立刻数错**：

- **13 行的「状态」与「提交」两列写反了**（全部是 R4 写的那批）。
  于是"按状态统计条数"这件事在此之前做不了：同一张表会数出两种结果。
  两列是机械可判的（状态只可能是图例里那四个值），所以这是纯粹的排版缺陷，不是判断分歧。
- `L-04` 那行里写着 `\ | \ | true`（源码里的 `||` 运算符）。GFM 里 `\|` 才是转义竖线，
  写成 `\ | \ |` 会导致**按竖线切分切出 7 格** —— 这一行此前在结构上就不合法。
- `M-08` 的提交列写成 `R3（随 H-13 一并改）/ docs/...`，不符合"`RN / 文档`"的形状。

三处都已规范化。并且新增 `tools/audit/check_ledger.py` 挂进 CI，它检查四件不需要判断力的事：
ID 唯一、**状态列只能是图例里的四个值**、标为「已修/不修」的行必须写明轮次与文档、
**引用的文档必须真的存在** —— 最后一条专治本目录的一个旧病：
`99-unverifiable.md` 被索引引用过整整 5 轮，**而那个文件直到 R6 才被真正创建**。

> 这条和 §4 是同一个模式：**一个不能被机械读出的索引，和一个会骗人的检查器是同一种东西。**
> 区别只是前者骗的是统计，后者骗的是结论。

### 5.6 同一个模式又一次：负向测试被自家门禁改红

`test_check_doc_refs.py` 里那条"把数字声明整句删掉也必须失败"的用例，原本这么写：

```python
changed = self.original.replace('主源 `.kt` 共 **77 个文件、21527 行**', '主源若干文件')
self.assertNotEqual(self.original, changed)      # ← 这行救了它
```

而 §1 的收口把 README 里的这个数从 `21527` 改成了 `21533`。于是 `replace()`
一个字符都没匹配上，`changed` 与 `original` 完全相同 —— 用例根本没做突变，
再拿去"验证删掉声明会失败"自然失败。**这一次红，是 §5.5 那个模式的第三例：
写死的字面量，在它描述的机制被修好之后失效。**

两件事值得单独记下来：

1. **它是红的，不是绿的 —— 因为多写了一个断言。** 如果当初图省事只写
   `run_on(self.original.replace(...))` 就断言退出码非 0，那么这个用例在
   README 数字变动的当天就**静默退化成一个什么都没测的空操作**，而且照样打印 OK。
   把"突变是否真的发生"也断言掉，才把一个会腐烂的绿灯换成一个会说话的红灯。
   这是本轮唯一一次由测试自己指出测试失效，不是人读代码读出来的。
2. **修法不是把 `21533` 填回去。** 填回去只是把下一次腐烂的时间往后推：
   §1 的门禁本来就是用来让这个数字继续变的。改成从校验器自己的正则里切出声明跨度：

   ```python
   what, pat, _expect = check_doc_refs.NUM_CLAIMS[0]
   m = pat.search(self.original)
   self.assertIsNotNone(m, f'README 里已找不到这项数字声明，用例已失效: {what}')
   changed = self.original[:m.start()] + '主源若干文件' + self.original[m.end():]
   ```

   这样被测对象（校验器认的那条声明）与突变目标由**同一个正则**定义，数字怎么
   漂移都测的是同一件事；而 `assertIsNotNone` 把"声明本身消失"这种失效也变成
   显式的红，而不是又一次空操作。**测试里凡是写死"被改动的原文"，都要问一句：
   这句原文以后会不会被它自己那套机制改掉。**

## 9. 主要发现：12 条门全绿 与 8/15 个提交带真实值 同时成立（B-02）

它的交接单 §0 写"脱敏、git 历史挖除……全部做完且全绿"，总表把 B-01 标成"已修 / R1"，
R1 的提交说明写"把真实取件码与真实小区名从 git 对象库里挖掉"。复测（命令见 §10.1）：

* 它自带的形状判据：`✓ 历史对象里没有 BLOCK 级命中`，退出码 **0**。
* 本轮新增的精确值判据：**8 / 15 个提交**携带作者本人的真实取件码与真实小区名
  （落在 `docs/audit/01-desensitization.md` 与 `tools/audit/redact_history.py`，
  即 R1…R6 与交接单提交），加上 `Initial release` 提交里的解析器注释。

**根因不是漏扫，是判据结构**：`scan_history.py` 只有 `BLOCK` 级参与退出码，
而真实取件码命中的 `PICKUP_CODE_COMPOUND` 是 MED、真实小区名命中的 `CN_ADDR_COMPOUND`
是 HIGH —— 两条**永远不可能让门失败**。把它们定成低严重度的理由本身站得住
（夹具与真实数据同形），所以这不是写错，是**形状判据的能力边界**。

补上的第二条判据分 A/B 两级：

| 级 | 内容 | 进退出码 | 为什么 |
|---|---|---|---|
| **A** | 手机号、居住地专名、本轮脱敏经手的值 | **是** | 仓库里没有任何正当理由写下它们 |
| **B** | 取件码形状值 | 否，只报命中提交 | 与夹具**同形同值**；实测 1920 个值命中 15/15 个提交，全是噪声 |

A 级 638 个值由本机 59 个私有语料文件（727 万字符）派生，**不入库**；派生时排除
带占位标记（`XX`、`示例`、连续升序数字等）的匹配 5086 次。**这个排除有代价** ——
它也会排掉"真实地名恰好含数字"的情况，所以经手的值是无条件并入清单的，
并且清单带一条**覆盖自检**：已知真实值必须命中，否则判定派生出错（防"清单空了也绿"）。

## 13.2 第三轮复核：按**校验和**判，不按形状判（同日）

用户点名的那几类（手机号 / 真实地址 / 门牌号 / 银行卡 / 身份证 / 密钥 / 签名）逐类重查。
这一轮的原则是**能用校验和的地方不用形状**：形状匹配在"6 位数字串"上必然刷出一堆
颜色常量，而 Luhn / 身份证校验位 / 文件哈希不会。

| 类别 | 判据 | 结果 |
|---|---|---|
| 银行卡 | 全树 `\d{16,19}` 候选 **1 个**，逐个过 **Luhn** | **0 个通过** ⇒ 不是卡（那 1 个是文档里的合成示例） |
| 身份证 | 18 位 + **校验位**（权重 7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2 → mod 11）；另查 15 位老式 | 候选 **0 个** |
| 手机号 | 4 种写法（纯 11 位 / 带空格连字符 / +86 / 掩码） | 只有 4 个值：`13800138000`、`138xxxx1234`、`187-1234-5678`、`18712345678`，全是夹具 |
| **那些"夹具号"是不是真号** | 把 4 个夹具值拿去**反查私有语料** | **一个都不在语料里**；也没有任何真实号以 `1871234`/`1380013` 开头 ⇒ 夹具标注属实，不是"洗白的真号" |
| 座机 | 区号+号码（含分隔写法） | 只有测试夹具 `010-12345678` |
| 带地名的门牌 | 语料 96 种 `中文名+数字号楼/单元/室` ∩ 发布树 | **0 命中**（纯门牌 `3号楼`/`12室` 有重叠，但它们不指向任何地点） |
| 地址串 | 语料 221 种含通名的串 ∩ 发布树 | 命中的全是通用词：`菜鸟驿站`/`通用小区`/`全链路`/`已到达驿站` |
| 密钥 | JKS magic `0xFEEDFEED`、PEM（RSA/EC/PKCS8/PGP）、`gh*_`/`AIza`/`AKIA`/`xox*`/`sk-` 前缀、高熵 ≥32 字符串 | 全部无；高熵候选 7 个全是文件路径与 Gradle 常量（`distributionBase=…`） |
| 口令 | `password|secret|token|apikey` 赋值 | 只有 `System.getenv("PICKUP_KEYSTORE_PASSWORD")` 与 README 里的 `export …=...` 占位 |
| 签名与凭据文件 | 受跟踪文件清单 + APK 内 `META-INF/*.RSA|DSA|EC` | 无 `.jks/.keystore/.p12/.pfx/.pem/.pk8/.key/.apk/.aab/.so/.aar/mapping.txt/local.properties/google-services.json`；两个 APK 都是 **unsigned** |

**一处口径自纠**：上一轮我口述"语料 11 位手机号 6575 个"是错的 —— 那个正则没加
`(?<!\d)…(?!\d)` 锚定，长数字串（例如运营商的短信中心号）会被切开，切出来的片段
恰好满足手机号形状。锚定后的正确数字是 **103 个**。
结论不受影响（当时的比对是在"超集"上做的，超集都 0 命中 ⇒ 子集必然 0 命中），
但这个数字本身该纠正 —— 口径错了就没人能复算。

> **这条自纠第一次写出来时，我把那个"切出来的片段"原样抄进了本文件** ——
> `scan_sensitive.py` 当场把它判成 BLOCK 级手机号命中，`test_repo_is_clean_now`
> 因此变红，整条发布链被自己挡住。第二次改成"例如运营商的短信中心号"这种**形状描述**。
> 这是同一类错误的**第三次**发生（我写过 README、另一条审计线写过 01-*.md 与
> redact_history.py）：审计文字越具体越可信，于是人会把值本身抄进证据栏。
> 结论：证据栏只写形状、位置与复现命令；**任何"举例"都不得包含值本身**。
